# 07. 大会一覧に検索・フィルタを追加する

- Status: planned
- Issue: #125
- PR: -

---

## 1. 背景・目的

`TournamentListPage`は取得した大会を`tournaments.map(...)`で全件`Grid`表示するのみで、大会名での
検索や状態(準備中/開催中/終了)での絞り込みが一切ない(`frontend/src/pages/TournamentListPage.tsx`)。
運営している大会数が増えるほど、目的の大会を探すために毎回一覧をスクロールする必要があり、最初に
開く画面としての使い勝手を落としている。

本計画は、大会一覧の上部に大会名(部分一致)検索と状態絞り込みを追加し、条件に一致する大会だけを
表示できるようにする。**フロントエンドの表示専用**とし、バックエンドAPI・データ取得ロジックには
一切影響しない(Issue #125「制約・やらないこと」)。ソート機能は本計画のスコープ外。

**最重要原則: 正確性 > シンプルさ > コスト > 機能 > 速度**

## 2. 画面シナリオ

- 運営者が 大会一覧画面で 大会名の一部を検索欄に入力すると 大会名にその文字列を含む大会だけが
  (大文字小文字を区別せず)即座に絞り込み表示される
- 運営者が 大会一覧画面で 状態フィルタから「開催中」を選ぶと 開催中の大会だけが表示される
- 運営者が 検索文字列と状態フィルタを両方指定すると 両方の条件を満たす大会だけが表示される(AND)
- 運営者が 検索・フィルタの結果0件になる条件を入力すると 「条件に一致する大会がありません」という
  空状態と、条件をリセットする導線が表示される
- 運営者が 大会が1件も無い状態(初期状態)で 一覧画面を開くと 検索・フィルタのツールバー自体は
  表示されず、既存の「大会がまだありません」の空状態のみが表示される(絞り込む対象が無いため)
- 運営者が 一覧取得中・取得エラー時に 画面を開くと 検索・フィルタのツールバーは表示されず、
  既存のローディング・エラー表示のみになる(データが無い状態でツールバーを操作可能に見せない)

観点の抜けチェック:

- 対象は運営者(PC)のみ(参加者向け共有ページに大会一覧は存在しないため該当なし)
- 個人戦・団体戦・グループ分けの有無による挙動差は無い(検索・フィルタは大会単位のメタ情報のみが対象)
- 競合・権限外アクセス: 一覧取得自体の認可は既存の`useTournaments`(`GET /tournaments`)にそのまま
  従う。検索・フィルタはクライアント側の表示処理のみで、追加のAPI呼び出し・認可判定を持たない

## 3. UI仕様

対象画面は `TournamentListPage`(S03 大会一覧)のみ。新規画面の追加ではないため、レイアウトへの
影響は既存の見出し行の下にツールバー1行を追加する範囲にとどめる。

### 大会一覧(TournamentListPage)

- **レイアウト構成**(上から順):
  1. 既存: 見出し「大会一覧」+「大会を作成」ボタン(変更なし)
  2. 追加: 検索・フィルタツールバー(大会が1件以上取得できている場合のみ表示)
  3. 既存: 大会カードの`Grid`(絞り込み後の一覧)、または空状態
- **主要要素(ツールバー)**:
  - 大会名検索の`TextField`(`InputAdornment`に`SearchIcon`、placeholder「大会名で検索」、
    `aria-label="大会名で検索"`)。デスクトップでは幅を持たせつつ`Select`より広く、モバイルでは
    `fullWidth`
  - 状態フィルタの`Select`(`aria-label="状態で絞り込み"`)。選択肢は「すべて」(初期値・空文字)/
    「準備中」/「開催中」/「終了」(`tournamentStatusLabels`をそのまま使う)
  - ツールバーは新規コンポーネント`TournamentSearchToolbar`
    (`frontend/src/components/features/tournament/TournamentSearchToolbar.tsx`)に切り出す
    (`TournamentCard`と同じ`features/tournament`配下。ページ側は状態管理と絞り込み結果の算出のみ持つ)
- **4状態の見せ方**:

  | 状態 | 表示 |
  |---|---|
  | 通常 | ツールバー + 絞り込み後の大会を既存の`Grid`表示(`TournamentCard`は変更なし) |
  | 空(0件) | ① 大会が0件(未フィルタ): 既存の`EmptyState`(「大会がまだありません」+「最初の大会を作成する」)をそのまま維持、ツールバーは非表示。② フィルタ結果が0件: 新しい`EmptyState`(メッセージ「条件に一致する大会がありません」、action=「検索条件をクリア」ボタンで検索文字列・状態フィルタを両方リセット) |
  | ローディング | 既存の`LoadingState`のまま(ツールバーは表示しない) |
  | エラー | 既存の`ErrorState`(メッセージと再試行導線)のまま(ツールバーは表示しない) |

- **大量データ時**: 最大300大会想定でも全件クライアント側`Array.filter`のみで、ページングや
  仮想化は行わない(既存の一覧表示自体がページングなしのため、フィルタもその前提を継承する。
  受け入れケース台帳の out-of-scope「一覧APIのページネーション」と整合)
- **レスポンシブ**: 375pxでは検索`TextField`と状態`Select`を縦積み(`Stack`, `direction={{ xs: 'column', sm: 'row' }}`)。デスクトップ(`sm`以上)では横並びで検索欄を広めに確保する
- **既存画面との一貫性**: 状態選択は`TeamTable`のグループ選択`Select`(`SelectDisplayProps`で
  `aria-label`を明示するパターン)に合わせる。検索アイコン付き`TextField`はこのリポジトリに
  前例が無いため新規パターンとして扱う(下記「新しいUIパターン」参照)
- **新しいUIパターンの有無**: あり。検索`TextField`+状態`Select`のツールバー構成は
  `02_component_design.md`に前例が無いため、実装PRで同ドキュメントに追記する
  (本Plan PRでは更新しない。§6参照)

## 4. 技術設計

- **レイヤーごとの変更点**: フロントエンドのみ。backend(domain/application/presentation/
  infrastructure)への変更は無い
- **API変更**: 無し。`schema/openapi.yaml`の更新も無い
- **データモデル**: 変更無し
- **フロントエンド**:
  - 追加コンポーネント: `frontend/src/components/features/tournament/TournamentSearchToolbar.tsx`
    (props: `searchText` / `onSearchTextChange` / `statusFilter` / `onStatusFilterChange`。
    制御コンポーネントとし、状態自体は呼び出し側の`TournamentListPage`が`useState`で保持する)
  - `TournamentListPage`側: `searchText`(string, 初期値`''`)・`statusFilter`
    (`TournamentStatus | ''`, 初期値`''`=すべて)を`useState`で保持し、`useMemo`で
    `tournaments`から絞り込み結果を算出する。絞り込みは大会名の部分一致
    (`name.toLowerCase().includes(searchText.trim().toLowerCase())`、空文字は常に一致)と
    状態の完全一致(`statusFilter === '' || tournament.status === statusFilter`)のANDのみで、
    新しいhookやqueryKeyの追加は不要(サーバー状態ではなくUIローカル状態のため)
  - URLクエリパラメータへの同期・永続化は行わない(Issueのスコープに無く、一覧画面は毎回
    未フィルタで開く現状の挙動を維持する方がシンプル。将来必要になれば別Issueで検討する)
  - 空状態の「検索条件をクリア」ボタンは`searchText`/`statusFilter`を初期値に戻すだけで、
    データの再取得は発生しない
- **マッチング・順位計算**: 触れない

## 8. リスク・未確定事項

- 大会数が将来300件規模に近づいた場合のクライアント側フィルタのパフォーマンスは、現状の全件取得
  (ページングなし)を前提にする限り既存の一覧表示自体と同じ制約であり、本計画独自のリスクではない
- 検索・フィルタの状態をURLに載せない判断により、ブラウザの戻る操作や再読み込みでフィルタ条件が
  失われる。Issueのスコープ・現状の使い方(1画面内で完結する探索)では問題にならないと判断したが、
  運用開始後に「フィルタ済みURLを共有したい」等の要望が出た場合は別Issueで再検討する
