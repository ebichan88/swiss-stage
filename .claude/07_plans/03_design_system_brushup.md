# 03. デザインシステムのブラッシュアップ(共有ページのパイロット改装)

- Status: in_progress
- Issue: #115
- PR: #118

---

## 1. 背景・目的

現行UIは見た目が「MUI標準そのまま」に寄っており、`02_design_system/00_basic_design.md` §1 が掲げる
コンセプト(「和の競技にふさわしい、落ち着いた品のある見た目」)と、それを受けて
`01_design_principles.md` §1 が定義する基調色(`primary.main` = 深緑 `#1B5E43`)が、画面に表れていない。

実態は `frontend/src/theme/index.ts` が示している。102行のうち大半がトークン定義で、
`components` の styleOverrides は `MuiButton`(textTransform / disableElevation)と
`MuiCssBaseline`(scrollbarGutter)の2つだけ。**残りはすべてMUIの既定値**である。

これはファーストリリース時に「低コスト・シンプル・既存コンポーネントライブラリに準拠」を
優先した判断の結果であり、コンセプト自体が誤っているわけではない。したがって本計画は
**新しいデザイン方向性を発明せず、既存コンセプトを画面に表出させる**ことを目的とする。

完了時に得られる状態:

- 参加者が最も多く触れる共有ページ(S10)・結果入力(S11)が、コンセプトを体現した見た目になっている
- デザイントークンが刷新され、`01_design_principles.md` と `theme/index.ts` が同期している
- `frontend-design` skill がリポジトリに入り、以後のUI実装で継続的に使える
- #112 で獲得したアクセシビリティ水準が維持され、**回帰を機械検査で防げる**状態になっている

**最重要原則: 正確性 > シンプルさ > コスト > 機能 > 速度**

意匠の都合で正確性(結果の読み違い防止)を落とさない。特に勝敗表示・順位表示は、
見た目を変えても「誤読しにくさ」が現状より悪化してはならない。

## 2. 画面シナリオ

**本計画は挙動を変更しない。** 画面シナリオは現行のままであり、以下は
「改装後も一字一句そのまま成立していること」を確認する回帰対象として列挙する。

- 参加者が 共有URLをスマホで開くと 大会名・状態・現在ラウンドと組み合わせタブが表示される
- 参加者が 組み合わせタブで 自分の卓を探すと 卓番号・対戦相手・結果・申告状態が読み取れる
- 参加者が 対局カードの「結果入力」を押すと 結果入力画面へ遷移する
- 参加者が 結果入力画面で 自分がどちらかを選び 勝敗を選ぶと 確認ダイアログが出て、申告すると組み合わせタブへ戻る
- 参加者が 申告済みの対局を再度開くと 誰が何を申告したかが表示される
- 参加者が 申告不一致の対局を開くと 警告(warning)が表示され、運営者への連絡が案内される
- 参加者が 順位表タブを開くと(ラウンド1確定後)トップ3のメダルカードと4位以降のリストが表示される
- 参加者が ラウンド1確定前に順位表タブを開くと 空状態が表示される
- 参加者が 対戦結果タブを開くと 戦績一覧表が表示される
- 参加者が 無効・失効した共有URLを開くと 「このURLは無効です」が表示される
- 参加者が 結果入力が締め切られた対局を開くと 締切の案内が表示され入力できない

観点チェック:

- 運営者(PC)側の画面は**構造を変更しない**。ただしトークン刷新の影響は受ける(§4)
- 個人戦のみをパイロット対象とする。団体戦(`TeamSharedPage` / `SharedTeamResultPage`)は構造改装の対象外
- グループ分けあり/なしの分岐(`multiGroup`)は現行どおり維持する

## 3. UI仕様

### 3-1. 本セクションの位置づけ(通常の機能追加との違い)

通常の機能追加ではここでレイアウトと状態を文章で確定させる。しかし本計画は
**具体的な意匠を探索して決めること自体がタスク**であり、計画段階で色値やレイアウトを
確定させることはできない。

そこで本セクションでは以下を確定させる。**これが実装PRの制約条件になる。**

1. 動かしてはいけない不変条件(§3-2)
2. 動かしてよい範囲(§3-3)
3. 探索の進め方と go/no-go の判断基準(§3-4)
4. 改装対象画面の現行構造と、変更してよい/いけない要素(§3-5)

具体的なトークン値・レイアウトは探索ステップの成果物として決定し、
**実装に入る前に `01_design_principles.md` へ記載する**(CLAUDE.md「新しいデザイントークンは
対応ドキュメントに追記してから使う」を満たすため)。

### 3-2. 不変条件(意匠の都合で動かさない)

利用者層(20代〜70代)と競技特性(結果を誤読できない)に由来するため、
デザイン方向性がどう決まっても動かさない。

| 不変条件 | 出典 |
|---|---|
| デザイン3原則(明快・堅実・信頼) | `00_basic_design.md` §1 |
| 画面の設計優先度(共有ページ > 結果入力 > 順位表 > 運営者管理画面) | `00_basic_design.md` §4 |
| タップターゲット最小44x44px / 結果入力ボタン56px以上 | `01_design_principles.md` §3 |
| 共有ページ本文の最低16px(高齢参加者配慮 + iOS自動ズーム防止) | `01_design_principles.md` §2 |
| テキストと背景のコントラスト比 WCAG AA(4.5:1)以上 | `01_design_principles.md` §1 |
| 勝敗を色だけに頼らない(○/● 記号を必ず併記) | `01_design_principles.md` §1 |
| 順位表の並び替えアニメーション禁止(順位が動いて見えると誤読リスク) | `03_animation_system.md` §4 |
| 数字の等幅表示(`tnum`。順位表の桁揃え) | `01_design_principles.md` §2 |
| ダークモード非対応 | `01_design_principles.md` §4 |

### 3-3. 動かしてよい範囲

ファーストリリース時の低コスト判断が出どころであり、今回見直してよい。

- **カラーパレットの具体値**(Issue #115 の決定: パレットごと刷新する)
- タイポグラフィスケール(variant ごとのサイズ・ウェイト・行間・字間)
- `elevation 0〜2 のみ` / `角丸8px 一律` という制約そのもの
- 情報密度・余白の取り方、罫線と面の使い分け
- `00_basic_design.md` §4 の「運営者管理画面は機能性優先でMUI標準に寄せてよい」という逃げ道
- `theme.components` の styleOverrides を増やすこと(現在ほぼ空)

### 3-4. 探索の進め方と go/no-go

```
① skill追加 + 不変条件の確定(本計画のマージで完了。skillは本PRで追加済み・§6参照)
    ↓
② frontend-design で共有ページの意匠を探索(Storybook上)
   既存の SharedPage.stories.tsx(S10)と SharedResultPage.stories.tsx(S11)の両方を対象にする
    ↓
③ 実機(スマホ実寸)で確認 → go / no-go を人間が判断   ← ここが唯一のゲート
    ↓ go
④ トークン確定 → 01_design_principles.md 更新 → theme/index.ts 実装
    ↓
⑤ 共有ページ・結果入力の改装 → 全画面の追従確認
    ↓
⑥ fixing-accessibility 再実行 → frontend-design の自己批評 + reviewer で仕上げ(§4-4)
    ↓
⑦ VRTベースライン更新
```

**go/no-go の判断基準**(③で人間が見るもの):

- 3原則(明快・堅実・信頼)が現行より強まっているか。特に「一目でわかる・押し間違えない」が後退していないか
- コンセプト(和・落ち着いた品)が言われなくても伝わるか
- 会場の環境(明るい照明・急いでいる・スマホを片手持ち)で読めるか
- 不変条件(§3-2)を1つも破っていないか

no-go の場合は②に戻る。②〜③はコードをmainに入れないため、破棄コストはStorybook上の作業のみ。

**本PRでの③の実施方法**: 物理スマートフォンではなく、Storybookのモバイルビューポート(375px)を
CIと同じPlaywrightコンテナ(フォントレンダリングが実機と一致)でスクリーンショットし、
それをユーザーに提示してgo/no-go判断を得た。判断の主体(人間)と判断基準(上記4点)は
維持しているが、「会場の環境(明るい照明・スマホを片手持ち)」の物理的な確認は行っていない。
これは今回の実装がリモート環境で行われ物理端末を用意できなかったための代替であり、
恒久的にこの手順を置き換えるものではない。次回以降、実機での最終確認を別途行うことを推奨する

### 3-5. 改装対象画面の現行構造

#### S10 共有ページ(`SharedPage.tsx` — 個人戦)

├─ 「組み合わせへ戻る」(text button + ArrowBackIcon)
├─ Card(variant="outlined")
│  └─ CardContent
│     ├─ 「第Nラウンド・X卓」(body2, text.secondary)
│     ├─ 「A vs B」(h2/h1)
│     ├─ ReportStatus(確定結果 / 双方の申告内容 / Alert: info・warning)

### 3-6. 4状態・レスポンシブ・大量データ

いずれも**現行の挙動を維持する**。改装で失わないことを確認する対象として明示する。

**S10 共有ページ**

| 状態 | 表示(現行・維持) |
|---|---|
| 通常 | タブ切替で 組み合わせ / 順位表 / 対戦結果 |
| 空(0件) | `EmptyState`。大会開始前・組み合わせ未生成・順位未確定・戦績なしでメッセージを出し分け |
| ローディング | `FullPageSpinner` |
| エラー | `ErrorState`(再試行ボタン付き)。無効トークンのみ専用画面(「このURLは無効です」) |

**S11 結果入力**

| 状態 | 表示(現行・維持) |
|---|---|
| 通常 | 「あなたはどちらですか?」→ 勝敗の選択 → `ConfirmDialog` の2段階 |
| 空(0件) | **該当なし**(一覧を持たない画面のため)。代わりに対局が特定できない場合 ——`mid` が不正、またはBYE(`player2 === null`)—— に「対局が見つかりません。組み合わせを確認してください。」+ 戻る導線を出す |
| ローディング | `FullPageSpinner` |
| エラー | `ErrorState`(再試行ボタン付き)。送信失敗はSnackbar(error)で通知し、同じ画面から再試行できる |
| 締切後 | 「この対局の結果入力は締め切られています」+ 運営者への連絡案内。選択UIは出さない |

いずれの状態も改装後に維持する。特に S11 の「対局が見つかりません」「締切後」は
`EmptyState` を使っていない独自表示のため、意匠を変える際に見落としやすい。

- **レスポンシブ**: 375px を主対象とする(参加者はスマホ)。共有ページは `maxWidth="md"`、
  結果入力は `maxWidth="sm"`。デスクトップでは中央寄せの1カラムのまま。この方針は変えない
- **大量データ時**: 300人・全ラウンドで、順位表は4位以降のリストが縦に伸び、
  戦績一覧表は横スクロールする。改装で横スクロールの成立条件を壊さないこと
  (テーブルの最小幅・セル余白を増やす場合は 375px での確認が必須)

### 4-1. レイヤーごとの変更点

### 4-2. トークン刷新の波及範囲(パレット全面刷新のため広い)

Issue #115 の決定「トークンは全画面に効かせ、コンポーネント改装は共有ページのみ」に従う。
`src/` 配下のハードコード色は **0件**でスタイルがすべてテーマ経由のため、
トークン差し替えは全画面へ自動伝播する。裏を返すと**確認範囲は全画面**になる。

| 影響先 | 内容 | 対応 |
|---|---|---|
| 共有ページ・結果入力 | 改装対象 | §3-5 のとおり再設計 |
| 運営者管理画面(全ページ) | トークン追従のみ | 構造は変えない。表示崩れ・コントラスト低下がないか確認 |
| `RankingBoard` / `TeamRankingBoard` | `rank.gold/silver/bronze` を参照 | **新パレットとの再調和が必要**。メダル色が浮かないか確認 |
| `MatchResultsTable` / `PairingTable` / `ParticipantTable` | ヘッダーが `primary.main` + 白文字、ゼブラが `background.paper`/`default` | primary 変更時に**白文字のコントラストAA割れが起きないか必ず確認** |
| 印刷帳票(`components/features/print/` 9ファイル) | `theme.print` + `text.primary` / `divider` を参照 | モノクロ運用(`headerBg` 薄グレー・緑ベタ塗り禁止)を維持。手書き罫線が薄くならないこと |
| `StatusBadge` | success / warning / info / default の Chip | セマンティックカラー変更時に判別性を確認 |

**特に注意**: `primary.main` は「表ヘッダーの白文字背景」と「主要ボタンの背景」を兼ねている。
明度を上げると白文字が AA を割り、下げるとボタンが重くなる。ここが今回のパレット刷新で
最も制約が強い点であり、探索段階で先に決めるべき値である。

#### `frontend-design` の適用条件

このプロジェクトと相性がよいのは中核メソッドの **"Ground it in the subject"**(題材の世界・素材・
道具・固有の言い回しから独自性を導く)である。囲碁・将棋は素材が豊かで(碁盤の格子・碁石の白黒・
駒の五角形・棋譜の記法・対局時計・段級位の表記体系)、現行UIはこれをほとんど使っていない。
ここが最大の伸びしろであり、②の探索ではこの語彙を明示的にブリーフに含める。

第1パスの出力形式(4〜6個の名前付きhex + 2種以上の書体ロール + レイアウト構想 + signature要素)は、
本計画が実装前に確定させたいもの(新パレット + タイポスケール → `01_design_principles.md`)と
ほぼ一致するため、そのまま成果物として使える。

ただし SKILL.md はランディングページ的な文脈で書かれており、次の3点は**枠付けしてから使う**。

| SKILL.md の記述 | 本プロジェクトでの補正 |
|---|---|
| 「hero は主張であれ」「signature要素を1つ持て」 | 運用ツールであり、騒がしい会場で急いでいる20〜70代が使う。装飾を順位表・対局カードに持ち込まない。§3-2 の不変条件と3原則が優先 |
| 「display と body の書体を意図的にペアリングせよ」 | 和文ディスプレイ書体の追加は**原則しない**。既に Google Fonts から Noto Sans JP(400/600/700)を配信しており、和文をもう1書体足すと配信量が重くなる(EC2 t3.micro・予算 ~$17/月)。ウェイト・サイズ・字間での階層付けを優先する |
| 「ページロード演出・スクロール連動・アンビエント」 | **不採用**。`03_animation_system.md` §4 でページ全体のトランジション演出・パララックス・スクロール連動演出を禁止済み |

また `frontend-design` は `primary.main` の制約(§4-2 の「表ヘッダーの白文字AA」と
「主要ボタンの重さ」の両立)を知り得ないため、**ブリーフに条件として明示的に渡す**。

#### `baseline-ui` を採用しなかった理由

当初は⑥の仕上げチェックに `ibelick/ui-skills` の `baseline-ui` を使う計画だったが、
SKILL.md を精査した結果**採用しない**と判断した。

- Tailwind CSS + Base UI/Radix + `motion/react` を前提に書かれており、MUI + Emotion 構成の
  本プロジェクトとはルールの大半が噛み合わない
- 特に `MUST use motion/react`(= framer-motion)は `03_animation_system.md` §4 の
  「アニメーションライブラリの追加禁止」と正面から衝突する。
  `MUST use Base UI / React Aria / Radix` も primitive の混在を招く
- スタック非依存で採用できる指摘(約10件)を既存ドキュメントと突き合わせたところ、
  7件は既出(200ms以内・`prefers-reduced-motion`・空状態の次の行動・等幅数字・アクセント1画面1つ 等)、
  2件は該当なし(グラデーション・`blur()` をそもそも使っていない)で、
  **実質的な増分は「compositor プロパティ(`transform`/`opacity`)のみを動かし、
  レイアウトプロパティを動かさない」の1件のみ**だった
- その1件のために、以後のセッションが「どのMUSTを無視すべきか」を毎回確認する必要が生じる。
  失敗モードが沈黙(素直に従うと禁止ライブラリが入る)であり、割に合わない

**増分の1件は `03_animation_system.md` に直接追記する**(実装PR。§6)。

⑥の仕上げ工程は次で代替する:

- `frontend-design` 自身の自己批評パス(SKILL.md の "critique, build, critique again" /
  「鏡を見てアクセサリーを1つ外す」)
- `fixing-accessibility` skill
- 既存の reviewer エージェントと `04_quality/01_review_checklist.md`

> 実装PRで、`frontend-design` の適用条件を `00_basic_design.md` へ昇格させるか検討する。
> 本計画は完了後に凍結されるため、恒久的な規約はプランではなく設計ドキュメント側に置く。

## 5. 受け入れケース

Prefix は `SHR`(共有)。既存最大 `SHR-AC-017` の次から採番する。

本計画は挙動を変えないため、新規ケースは**改装で壊れやすい不変条件を機械検査に落とすもの**に限る。
これは #112 のアクセシビリティ成果を回帰から守り、「うまくいかなければ切り戻す」判断を
安全にするためのガードでもある。

検証の性質は2種類に分かれる。**いずれもレイアウト計測に依存しない**
(jsdom では実レイアウトを測れないため、タップ領域44px等は自動検査の対象にしない)。

1. **テーマトークンそのものの検証**(SHR-AC-018 / 019)— `theme` オブジェクトの値を直接読む
   純関数的なテスト。レンダリング不要
2. **コンポーネントの描画内容の検証**(SHR-AC-020)— `SharedMatchCard` のマークアップに
   記号が出ているかを Testing Library で確認する。色の値ではなく**記号の存在**を見るため、
   パレットを変更しても壊れない

| ID | P | 受け入れ基準 | 検証手段 |
|---|---|---|---|
| SHR-AC-018 | P1 | 共有ページ・結果入力ページの本文タイポグラフィ(body1)が16px以上である | theme.test(Vitest) |
| SHR-AC-019 | P1 | テーマで定義した文字色と背景色の主要な組み合わせがWCAG AA(4.5:1)以上のコントラスト比を満たす | theme.test(Vitest) |
| SHR-AC-020 | P1 | 共有ページの対局カードは勝敗を色だけでなく記号(○/●)で併記する | SharedPage.test(Vitest) |

- SHR-AC-019 の「主要な組み合わせ」は最低限次を含む:
  `text.primary`/`background.default`、`text.primary`/`background.paper`、
  `text.secondary`/`background.default`、`primary.contrastText`/`primary.main`(表ヘッダー)、
  `error.main`・`success.main`・`warning.main` の各文字色/`background.paper`
- 優先度は `00_acceptance_policy.md` §4 の定義(P0/P1/P2)に従う。判定フローは同節が
  流用元として挙げる `02_severity.md` を用いる。
  **3件とも P1**: いずれも破られると「利用者が情報を読めない・読み違える」状態になり、
  仕様違反かつユーザー影響のあるバグに当たる(≒Major)。一方、大会当日に運営が止まる・
  結果が狂う・情報が漏れるには当たらないため P0 ではない。
  3件は「現行実装が既に満たしており、改装での回帰を防ぐ」という同一の性質を持つため、
  優先度に差を付けない
