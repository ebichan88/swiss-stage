# 13. 大会の共同管理を招待リンク + 大会単位のメンバーシップで実現する

- Status: Accepted
- Issue: #185
- Date: 2026-08-16

## 1. 文脈

これまで大会は「1ユーザーが所有する」構造で、`Tournament.ownerSub` と JWT の `sub` の一致を
`TournamentAccessSupport.loadOwned()` の1箇所で検証していた。実運用では複数のスタッフで大会を
分担したいという要求があり、特に当日の結果入力を1人が抱えるのは現実的でない。

決める必要があったのは3つ。**(a) 共同管理者をどうやって指定するか**、**(b) 権限を何段にするか**、
**(c) 組織(Organization)という概念を導入するか**。

制約として重いのは次の2点である。

- **ユーザーディレクトリが存在しない**。永続化されているのは大会だけで、`User` エンティティはない。
  認証はGoogleの `sub` を自前JWTに載せるだけであり、メールアドレスからユーザーを逆引きする手段がない
- **GSIは最大3本**という自己制約があり、うち2本(GSI1=運営者の大会一覧、GSI2=共有トークン)を
  既に使っている

## 2. 決定

- 共同管理者の指定は **招待リンク方式**とする。ユーザーディレクトリを作らず、メールアドレスも保存しない
- 権限は **OWNER / MAINTAINER の2段**とし、大会設定(S09)を丸ごと OWNER 専用にする
- メンバーシップは **大会パーティション配下の `MEMBER#{sub}` アイテム**として持ち、既存 GSI1 に
  相乗りさせる(既存データの移行を不要にする)
- 招待は **大会あたり1本の共通リンク + 人数枠 + 有効期限72時間**とする
- **組織(Organization)エンティティは導入しない**

キー設計・API・ライフサイクル・404/403の使い分けといった仕様の詳細は
`14_tournament_collaboration.md`(同じPRの実装計画)を参照する。

## 3. 却下した案

### (a) 共同管理者の指定方法

- **メールアドレスで指定する** → 却下。email から sub を引く索引(実質的なユーザーディレクトリ)が
  必要になり、しかも相手が一度もログインしていなければ引けない。加えて運営者のメールアドレスを
  DBに保持することになり、「保持する個人情報は必要最小限」(`13_security_design.md` §1)に反する
- **ユーザーIDを払い出して口頭で共有してもらう** → 却下。ディレクトリが必要な点はメール指定と同じで、
  さらに「相手に自分のIDを調べて教えてもらう」という往復が増える。招待リンクより体験が悪い

### (b) 権限の段数

- **参照専用ロール(VIEWER)を同時に入れる** → 却下。大会状況の共有は既存の共有リンク
  (`Visibility=TOKEN`)で満たせる。ロールを増やすと「権限 × 画面 × 大会状態」でテスト行列が
  掛け算で膨らみ、*正確性 > 機能* の原則に反する。ただし将来の追加が非破壊になるよう、
  永続化する値は boolean ではなく role の enum にした
- **共有URLの再発行だけ MAINTAINER にも開放する** → 却下。当日トークンが漏れた際に MAINTAINER が
  対処できないという利点はあるが、「設定画面は丸ごと OWNER 専用」のほうが説明しやすく、
  権限境界のテストも単純になる

### (c) 組織(Organization)

- **組織エンティティを先に作り、大会を組織に紐づける** → 却下。`ownerSub` 前提の既存サービス
  全体の書き換えが必要になり、後戻りが最も高くつく。実際のニーズ(毎年同じ運営チーム)は将来
  「前回の大会から共同管理者をコピーする」機能で満たせる見込みで、そのときも大会単位の
  メンバーシップはそのまま使える。順序として、大会単位のメンバーシップが先で組織が後なら
  非破壊に積めるが、逆はできない

### (d) メンバーシップの持ち方

- **METADATA アイテムに共同管理者の `sub` を配列で持つ** → 却下。GSI1 で「その人が共同管理する
  大会」を引けず、大会一覧を出すのに全走査が必要になる
- **すべてのメンバーシップを MEMBER アイテムに統一し、OWNER も MEMBER として持つ** → 却下。
  データモデルとしてはこちらが素直だが、既存の全大会に対する移行スクリプトが必要になる。
  マイグレーションは事故の温床であり、*正確性 > シンプルさ* の順序に照らして、
  「`ownerSub` を残したまま MEMBER を足す」非対称な形を受け入れた
- **メンバーシップ用に GSI3 を新設する** → 却下。GSI1 の `USER#{sub}` と用途が同じで、
  SK の形式を揃えれば1本のクエリで所有大会と共同管理大会を並び順ごと取得できる。
  GSI枠を1本残せる利点のほうが大きい

### (e) 招待リンクの寿命

- **1回使い切り(1人につき1本発行)** → 却下。漏洩時の被害が1人分に限定される利点はあるが、
  当日スタッフが5人いれば5本発行して個別に配る手間が生じる。共通リンク + 人数枠でも
  「期限72時間」「枠上限」「OWNERが承諾者を見て取り消せる」で実用上のリスクは抑えられる
- **無期限で失効操作のみ** → 却下。書き込み権限を伴うリンクが無期限に生き残る

### (f) 結果入力者の記録

- **対局アイテムに入力者の `sub` を保存する** → 却下。「誰が入力したか」は複数人運営では
  知りたくなるが、個人単位の監査ログは保持方針・削除方針・表示範囲を別途設計する必要があり、
  スコープが膨らむ。MVPでは `ResultInputBy` に `MAINTAINER` を足すだけに留める

### (g) `entryOrder` 採番の同時実行制御(共同管理の導入で顕在化した既存バグの直し方)

- **DynamoDBのアトミックカウンタ(`UpdateExpression: ADD nextEntryOrder :n`)を使う** → 却下。
  read-then-write を避けて1回の `UpdateItem` で採番できる利点はあるが、この経路だけ
  Enhanced Client の `TableSchema`(既存の `@DynamoDbVersionAttribute` による楽観ロック)を
  迂回した低レベルAPI呼び出しが必要になり、`Tournament` の更新経路が2種類(バージョン楽観ロック /
  アトミックADD)に分かれる。カウンタの増分と `Participant`/`Team` アイテムの作成はそもそも
  別アイテムへの2回の書き込みで、アトミックADDにしても操作全体の原子性は得られない
  (整合性の担保点は変わらず「採番の重複を防ぐ」だけに留まる)ため、原子性で得られる利益が
  経路が増える複雑さに見合わない
- **採用**: 既存の `@DynamoDbVersionAttribute` による楽観ロックをそのまま使う(§4.5の対策)。
  `Tournament` の更新(改名・公開範囲・共有トークン再発行等)がすでにこの方式に統一されており、
  競合時の挙動(409 → フロントの再試行メッセージ)も既存パターンをそのまま踏襲できる。
  CLAUDE.mdの優先原則(正確性 > シンプルさ)に照らし、単一の更新経路に寄せることを優先した

## 4. 結果

得たもの:

- 既存データの移行なしで共同管理を追加できる。`ownerSub` と GSI1 のキー形式を変えない
- 認可の変更が `TournamentAccessSupport` の1箇所に閉じる(全サービスがここを通っているため)
- GSI を増やさずに済み、上限3本に1本の余裕が残る
- メールアドレスを新たに保持せずに済み、保持する個人情報の増加は承諾者の表示名のみに留まる

引き受けたトレードオフ:

- **招待リンクは共通リンクであり、なりすまし対策ではない**。リンクを持つ第三者は枠が残っていれば
  共同管理者になれる。緩和は期限・枠・OWNERによる取り消しの3点
- **OWNER だけが MEMBER アイテムを持たない**という非対称な構造になり、認可コードは
  「`ownerSub` と一致するか」→「MEMBER アイテムがあるか」の2段判定になる
- **MEMBER アイテムが GSI1 に相乗りする**ため、GSI1 を引くすべてのクエリに `entityType` の
  フィルタが必須になる。付け忘れると既存の大会一覧が壊れる(この規約は `CLAUDE.md` の
  「避けるべき落とし穴」に追記する)
- **人数枠は共同管理者を取り消しても戻らない**。上限判定を1アイテムの条件付き更新に閉じ込めて
  同時承諾での枠超過を防ぐことを優先した

撤回条件:

- 「毎年同じ運営チームで複数大会を回す」運用が主流になり、大会ごとの招待が明確に負担になった場合は、
  組織エンティティの導入を新しいADRとして起こす(本ADRを `Superseded by` にする)
- なりすましが実際に問題になった場合は、招待を1回使い切りの個別リンクへ切り替える。この変更は
  INVITE アイテムの SK を `INVITE` から `INVITE#{inviteId}` に広げるだけで済むため、本決定を
  覆さずに補正できる
