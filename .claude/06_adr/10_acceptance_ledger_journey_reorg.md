# 10. 受け入れケース台帳をユーザージャーニー軸で再編し、作成基準を明文化する

- Status: Accepted
- Issue: #165
- Date: 2026-08-09

## 1. 文脈

受け入れケース台帳(`.claude/05_acceptance/01_acceptance_scope.md`)が151件(done149 / in_progress2 / todo0)に育った時点で、直近の追加(TRN-AC-015〜028)がほぼ全てP2のUI回帰であり、P0の中核(マッチング・順位計算)は増えていない。台帳を上から読んでも「このシステムは何をするものか」が分からない状態になっている。

原因は3つある。

1. **組織化の軸が技術構造**: `00_acceptance_policy.md` §2 がコンポーネント単位(=contractテストクラス=APIリソース境界)をPrefixに採用しており、この軸の上に「システムのユースケース」は現れない
2. **バグ修正が無条件に受け入れケースを生む**: `04_development_process.md` §2 のトリガー表がバグ修正に「再発防止を1件追加」を無条件で要求しており、ユーザーができることが何も変わらない修正でも台帳が1行伸びる構造的な増加圧力がある(例: TRN-AC-027, TRN-AC-028)
3. **UI系ケースが実装語彙で書かれている**: コンポーネント名・MUIのprop・カラーコードが受け入れ基準の本文に入っており、体験が同じままリネームしただけで基準が壊れる(例: TRN-AC-024)

制約: 既存IDの振り直しはしない・`docs-lint.py` は変更しない・テストの削除はしない(回帰テストとして残す)・E2E側のCP番号は変更しない。

## 2. 決定

台帳を**ユーザージャーニー軸**で再編し、受け入れケースの作成基準を明文化する。詳細な文面・移行対象・実装手順は同じPRのプラン(`.claude/07_plans/09_acceptance_ledger_journey_reorg.md`)を参照する。決定の要点のみ挙げる。

1. 台帳冒頭にユーザージャーニー節を新設する。中身は既存の E2E-AC-001〜009(CP1〜CP7)から起こし、新しく決める仕様はない
2. 受け入れケースを作る/作らないの判定基準として3条件(できることの変化/業務ルールの変化/大会当日の致命性)を `00_acceptance_policy.md` に明文化する
3. バグ修正の受け入れケース追加トリガーを、「仕様が欠けていた」場合のみに限定する条件付きルールへ変更する(`04_development_process.md` §2)。「仕様は正しく実装がミスしていた」場合は台帳を変更せず回帰テストのみ追加する
4. 既存151件を新基準に整合させる(昇格・統合・削除)。台帳から外すケースのテストは**回帰テストとして残し、IDタグのみ外す**(`(回帰)` マーカー等を台帳に残す方式は採らない)
5. `qa.md` の責務①(台帳整合)・④(不足提案)に、ジャーニーに属さない変更は台帳更新を求めない旨を反映する
6. 上記1・2・3・4・5の実際のファイル書き換えは**実装PR**で行う。本Plan PRはADRとプランのみを追加する(`04_development_process.md` §2 のARCH型トリガー表で受け入れケース列が「—」であることに整合させる)

## 3. 却下した案

- **案: 台帳に `(回帰)` マーカーを付けて残す** → 却下理由: テストと台帳の二重管理になり、`00_acceptance_policy.md` §1「同じ内容を複数の場所に書かない」に反する。テスト側にも同じ情報(回帰防止である旨)が残るため、台帳側にも書くと乖離の温床になる
- **案: 既存IDを振り直してジャーニー順に並べ替える** → 却下理由: `00_acceptance_policy.md` §3 のID永久欠番原則と `docs-lint.py` の双方向突合(台帳↔テスト)を壊すリスクが高く、Issue本文の制約「既存IDの振り直しはしない」にも反する
- **案: バグ修正の受け入れケース追加トリガーを完全撤廃する(常にケース追加不要)** → 却下理由: 本物の仕様欠落に由来するバグまで再発防止から漏れる。条件付き化(仕様欠落のみ対象)によって、台帳への増加圧力だけを取り除きつつ、バグ修正には必ずテストを付ける規律(`01_review_checklist.md` TEST系)自体は変えない

## 4. 結果

**得たもの**:

- 台帳の1画面目で「このシステムは何をするものか」が答えられるようになる
- バグ修正PRでの機械的な台帳肥大化が止まる(仕様が正しく実装だけがミスしていた場合は台帳を変更しない)
- UI系ケースの実装語彙依存が減り、コンポーネントのリネーム・リファクタに対する耐性が上がる

**引き受けたトレードオフ**:

- 既存151件のうち約12件(昇格候補+統合1件+削除6件、詳細はプラン参照)の書き換えコストが実装PRに乗る
- ジャーニー節と既存Prefix別セクションの二重管理を避けるため、ジャーニー節はE2E-AC参照のみに留め、仕様の詳細は書かない運用規律が今後も必要になる

**撤回条件**: ジャーニー軸での整理がかえって台帳を探しにくくする、またはQAエージェントの機械的な突合(`docs-lint.py` / `ai-qa.yml`)を阻害すると判明した場合、本ADRをSupersededとし技術構造軸に戻す。
