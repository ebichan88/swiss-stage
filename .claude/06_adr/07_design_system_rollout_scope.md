# 07. デザインシステム改装の他画面展開スコープ

- Status: Proposed
- Issue: #119
- Date: 2026-08-02

---

## 1. 文脈

Issue #115・PR #118 で共有ページ(個人戦)をパイロットとして改装し、go判定を得た
(`.claude/07_plans/03_design_system_brushup.md` §3-4)。パイロットは意図的に1画面に
スコープを絞っており(切り戻しを安く保つため)、対象範囲・展開方法を Issue #119 の
Plan PR で決めることになっていた(Issue #119 本文「制約・やらないこと」参照)。

決めるべき点は3つ:

1. **対象範囲**: Issue #119 が候補に挙げた結果入力ページ・RankingBoard/MatchResultsTable・
   運営者管理画面のうち、どれを展開対象にするか
2. **go/no-go判断の単位**: パイロットは1画面ごとにStorybook探索→実機確認→判断、という
   ゲートを設けていた。展開でも画面ごとに繰り返すか
3. **実装PRの分け方**: 画面ごとに分割するか、まとめるか

特に運営者管理画面は `00_basic_design.md` §4 に「機能性優先でMUI標準に寄せてよい
(構造・コンポーネント改装は対象外)」という明示的な逃げ道があり、これを維持するか
覆すかが焦点だった。

## 2. 決定

**対象範囲**: 次の3グループを展開対象に含める。個人戦の結果入力ページ(SharedResultPage)の
再改装は対象外とする(パイロットで検討済み・撤回済みのため。`03_design_system_brushup.md` §4-3)。

- (a) `RankingBoard`/`MatchResultsTable`(個人戦)と `TeamRankingBoard`/`TeamMatchResultsTable`
  (団体戦)。共有ページ・運営者管理画面で共用のコンポーネント
- (b) 団体戦の共有ページ(`TeamSharedPage`)・結果自己申告ページ(`SharedTeamResultPage`)。
  個人戦パイロットで確立した卓番号タイル・ヘッダー帯・アクセント線を団体戦にも展開する
- (c) 運営者管理画面の共通レイアウト(`TournamentLayout`)の見出し帯・ナビゲーション。
  ただし個別画面内部(参加者管理表・`PairingTable`・設定フォーム等)は対象外とし、
  `00_basic_design.md` §4 の「機能性優先でMUI標準に寄せてよい」を維持する

`00_basic_design.md` §4 の「運営者管理画面は構造・コンポーネント改装は対象外」を
上記 (c) の範囲に限定して撤回する(全面撤回ではない)。

**go/no-go判断の単位**: パイロットのような画面ごとの個別ゲートではなく、対象範囲を
まとめた単一のゲートで判断する。

**実装PR**: 対象範囲をまとめて1本とする。

## 3. 却下した案

- **画面ごとの個別go/no-goゲート**: パイロットと同じ慎重さを保てるが、既に確立した
  意匠パターン(卓番号タイル・ヘッダー帯等)の横展開であり、パイロットのような新規探索を
  伴わない。画面数分ゲートを設けるコストに見合わないと判断した
- **画面ごとの実装PR分割**: レビュー・切り戻しの粒度は上がるが、対象範囲全体でVRT差分を
  確認する手間が画面数分かかる。パターンが実質同一のため差分は予測しやすく、まとめて
  レビューしても見落としのリスクは低いと判断した
- **運営者管理画面を対象外のまま維持**: `00_basic_design.md` §4 の逃げ道をそのまま使う案。
  しかし共有ページと管理画面の見た目が混在すること自体がIssue #119 の根本課題であり、
  対象外のままでは解決しない。ただし全面改装まではせず、共通レイアウトの見出し帯・
  ナビゲーションのみに限定してリスクを抑えた(個別画面内部は現行どおりMUI標準)

## 4. 結果

**得たもの**: 参加者(個人戦・団体戦)・運営者の双方が触れる画面全体で、パイロットが
確立した意匠が一貫して展開される。実装・レビューコストは単一PRで完結する。

**引き受けたトレードオフ**: 単一ゲート・単一PRのため、対象範囲のどこかで問題が
見つかった場合、範囲全体の切り戻し判断が必要になる(画面ごとの部分マージという
選択肢を失う)。ハードコード色0件の原則(`03_design_system_brushup.md` §8)を維持し、
構造変更のコミットを画面単位で分けておくことで、必要になった場合の部分revertを
可能にする。

**撤回条件**: 一括go/no-goのレビューで対象範囲の一部にのみ問題が見つかった場合、
その画面の変更のみコミット単位でrevertする。対象範囲全体で3原則(明快・堅実・信頼)が
後退していると判断された場合は、(c) 運営者管理画面から先に対象外へ戻す
(パイロット同様、共有ページ側の優先度が最も高いため)。
