# 06. デザインシステムを「MUI標準に寄せる」方針から独自トークンの作り込みへ転換する

- Status: Proposed
- Issue: #115
- Date: 2026-08-02

## 1. 文脈

ファーストリリース時、デザインシステムは「低コスト・シンプル・既存コンポーネントライブラリに準拠」
という判断で構築した。その結果が現行の `frontend/src/theme/index.ts` である。

- 全102行。大半がカラー・タイポグラフィ・印刷のトークン定義
- `components` の styleOverrides は `MuiButton`(textTransform / disableElevation)と
  `MuiCssBaseline`(scrollbarGutter)の2つのみ
- **それ以外はすべてMUIの既定値**

この方針は `02_design_system/00_basic_design.md` §4 にも「運営者管理画面は機能性優先で
MUI標準に寄せてよい」という形で明文化されている。

結果として、同ドキュメント §1 が掲げるコンセプト——「和の競技(囲碁・将棋)にふさわしい、
落ち着いた品のある見た目」——と、それを受けて `01_design_principles.md` §1 が
基調色として定義する `primary.main` = 深緑 `#1B5E43` が、**画面上ではほとんど
知覚できない**状態になっている。トークンとしては定義されているが、それを表現に変換する
レイヤーが存在しないためである。

参加者が最も多く触れる共有ページ(S10)の印象が平凡なまま固定されることは、
大会運営プラットフォームとしての信頼感・体験価値の面で機会損失である。

一方で、この転換には以下の制約がある。

- 対象利用者は20代〜70代と幅広く、会場は騒がしく参加者は時間に追われている
- 扱う情報(対局結果・順位)は誤読が許されない
- #112 でアクセシビリティを改善したばかりであり、視覚刷新はこれを静かに壊しうる
- 予算 ~$17/月 の個人プロジェクトであり、デザイン専任者はいない

## 2. 決定

**「MUI標準に寄せる」方針を撤回し、デザイントークンと `theme.components` の styleOverrides を
作り込む方向へ転換する。**

ただし転換にあたり、次の3つを同時に定める。

### 2-1. 新しい方向性を発明せず、既存コンセプトを表出させる

デザインの方向性そのもの(和・深緑・落ち着いた品)は**変更しない**。
既存コンセプトは妥当であり、問題は実装がそれを表現していないことにあるためである。
`frontend-design` skill を使う際も「方向性の発明」ではなく「既存コンセプトの表出」を枠として与える。

### 2-2. 不変条件を意匠から切り離して固定する

次は利用者層と競技特性に由来するものであり、**意匠の都合で動かさない**。
詳細と出典は `.claude/07_plans/03_design_system_brushup.md` §3-2 に一覧化する。

- デザイン3原則(明快・堅実・信頼)、画面の設計優先度
- タップターゲット44x44px以上(結果入力56px以上)、共有ページ本文16px以上
- コントラスト比 WCAG AA(4.5:1)以上、勝敗を色だけに頼らない(○/● 併記)
- 順位表の並び替えアニメーション禁止、数字の等幅表示、ダークモード非対応

### 2-3. 段階導入とし、切り戻し可能な状態を保つ

全画面を一度に改装しない。共有ページ(S10)+ 結果入力(S11)をパイロットとし、
Storybook で探索 → 実機確認 → go/no-go を人間が判断してから他画面へ広げる。

トークン変更は全画面に伝播するが、`src/` 配下のハードコード色が **0件**であるため、
トークン差し替えコミットの revert で全画面が現行へ戻る。この性質を維持することを転換の前提とする。

### 2-4. 支援ツールの位置づけ

`.claude/skills/` に `frontend-design`(Anthropic公式)を追加する。中核メソッドである
"Ground it in the subject"(題材の世界・素材・道具・固有の言い回しから独自性を導く)が、
素材の豊かな囲碁・将棋という題材と噛み合うためである。適用条件は
`.claude/07_plans/03_design_system_brushup.md` §4-4 に定める。

**`baseline-ui`(ibelick/ui-skills)は採用しない。** 当初は仕上げチェックに使う計画だったが、
Tailwind CSS + Base UI/Radix + `motion/react` を前提に書かれており、本プロジェクト
(MUI + Emotion)とはルールの大半が噛み合わない。特に `MUST use motion/react` は
`03_animation_system.md` §4 の「アニメーションライブラリの追加禁止」と正面から衝突する。
スタック非依存で採用できる指摘を既存ドキュメントと突き合わせた結果、実質的な増分は
「compositor プロパティのみを動かす」の1件のみであり、その1件は `03_animation_system.md` へ
直接追記すれば足りる(詳細な検討結果は同 §4-4)。

導入判断の一般則として、**skill は「どのMUSTを無視すべきか」を毎回確認しなければ使えない
状態になった時点で採用しない**。逸脱が沈黙のうちに規約違反(禁止ライブラリの導入)を生む
ものは特に避ける。

## 3. 却下した案

### 案A: 現状維持(MUI標準に寄せ続ける)

**却下理由**: コンセプトが画面に表れていない問題が解決しない。デザインシステムのドキュメントと
実装が実質的に乖離した状態(トークンは定義済みだが表現に反映されない)が固定化し、
ドキュメントが形骸化する。

### 案B: 余白・タイポ階層の調整に留める(小幅な改善)

**却下理由**: リスクは最小だが、MUI既定値による「どのアプリでも見たことがある」印象は残り、
目的である体験価値の向上に届かない可能性が高い。ただしこの案は**撤退先として保持する**
(パイロットの go/no-go が2回 no-go になった場合はここへ落とす。§4)。

### 案C: MUI から別のUIライブラリへ乗り換える

**却下理由**: 現行実装はMUIに深く依存しており(Table・Dialog・Snackbar・Tabs・
Autocomplete等を広範に使用)、移行コストが目的に対して過大。
最重要原則「正確性 > シンプルさ > コスト」に反する。既存の動作するUIを作り直す過程で
正確性を落とすリスクも負う。

### 案D: 共有ページ専用のテーマを持ち、他画面と完全に隔離する

**却下理由**: 他画面への影響をゼロにできる点は魅力的だが、テーマが二重化して保守コストが
恒常的に上がる。また運営者画面と参加者画面で見た目が乖離し、同一プロダクトとしての
一貫性が損なわれる。トークン伝播による全画面の変化は、確認範囲が広がる代わりに
一貫性を保つ利点があると判断した。

### 案E: 全画面を一度に改装する

**却下理由**: 切り戻しがオールオアナッシングになる。パイロットを1画面に絞れば、
方向性が外れたときの破棄コストが Storybook 上の作業に留まる。

## 4. 結果

**得たもの**:

- デザインの表現力に上限がなくなり、コンセプトを画面で表現できるようになる
- 不変条件が意匠から切り離されて明文化され、今後どんなデザイン変更をしても
  アクセシビリティと誤読防止が担保される(SHR-AC-018〜020 で機械検査する)
- `.claude/skills/` の skill 群により、以後のUI実装で同じ品質基準を再利用できる

**引き受けたトレードオフ**:

- `theme/index.ts` の保守対象が増える。MUIのメジャーアップグレード時に
  styleOverrides の追従コストが発生する
- トークン変更のたびに全画面・印刷帳票・VRT全スクリーンショットが確認対象になる
- デザイン判断に人間のレビュー(実機確認)が必須になり、完全自動化できない工程が増える
- `primary.main` が「表ヘッダーの白文字背景」と「主要ボタン背景」を兼ねるため、
  パレット選択の自由度は見た目ほど高くない

**撤回条件**:

- パイロットの go/no-go で no-go が2回続いた場合、案B(小幅な改善)へ落とす
- マージ後にアクセシビリティ回帰・誤読の増加が判明した場合、トークン差し替えコミットを
  revert する。この撤回可能性を維持するため、**`src/` 配下に色をハードコードしない規約
  (`CLAUDE.md` 落とし穴7)は今後も厳守する**
