# 01. 上流プロセスの成果物をリポジトリに永続化する

- Status: Accepted
- Issue: なし(このシリーズ自体が `04_development_process.md` の前身にあたるため、Issueなしで開始した)
- Date: 2026-07-31

## 1. 文脈

下流工程(実装〜マージ)は reviewer / fixer / qa / qa-fixer / ci-fixer と guard.yml / docs-lint によって
自律的に品質を維持できている(`11_cicd_design.md`)。一方、上流(要件 → 仕様検討 → 実装計画)は
Claude Code の Plan モードの中だけで完結しており、次の問題があった。

- 検討結果は `~/.claude/plans/` のようなローカルの一時領域に残るのみで、**リポジトリの外**にある。
  clone しても付いてこない、grep できない、docs-lint も design-reviewer も届かない。
- 「なぜその設計にしたか」「どの案を却下したか」が失われる。既存の設計ドキュメントを見ても、
  `01_architecture_design.md` の決定表のように**理由が1行に圧縮され、却下案が残っていない**箇所が多い。
- 上流の品質ゲートが「人間の承認」1段しかなく、下流だけ自律化が進んでいる非対称な状態だった。
- 課題を認識していても着手時期が未定なものを置く場所がなかった(Issue 運用が存在しなかった)。

## 2. 決定

次のプロセスを導入する。

```text
人間: 要件・課題を書く
  → /issue → AI: Issue作成(分類テンプレート・優先度・対応時期)
  → /plan <issue番号> → AI: 不明点を質問 → Plan PR(コード0行。ADR・計画・受け入れケースtodo)
  → 人間: Plan PR を Approve & マージ    ← 承認はここだけ
  → /pr → AI: 実装PR(`Closes #N`)→ 既存の reviewer/qa/fixer/ci-fixer が回る
```

成果物は次の3種としてリポジトリに残す。

| 成果物 | 置き場所 | 役割 |
|---|---|---|
| Issue | GitHub Issues(テンプレート化) | 進捗の管理単位。着手時期未定でも記録できる |
| 実装計画 | `.claude/07_plans/NN_<slug>.md` | 画面シナリオ・UI仕様・受け入れケースなど、実装前に確定させる内容 |
| 決定記録(ADR) | `.claude/06_adr/NN_<slug>.md` | 複数ドキュメントにまたがる決定の経緯と却下案 |

計画レビュー用に `plan-reviewer` エージェントを新設するが、**非ゲート(レポートのみ)** で開始する(判断基準は本ADR §3 参照)。

## 3. 却下した案

### 案A: Issue本文に計画・設計検討を集約する

Issue本文だけで完結させ、専用のPlan PR・ADRディレクトリは作らない案。GitHub上で一覧性は高いが、
**リポジトリの外**にあるという上流の根本課題が解決しない: `.claude/**` の変更を検出する
design-reviewer が届かない、docs-lint がID整合やファイル参照を検査できない、clone した環境に
残らない。下流工程が git を正典にして自律化できているのと非対称になるため却下した。

Issueの役割は「一覧性・ステータス管理・`Closes #N` による自動クローズ」に絞り、本文は
Plan PR へのリンクと要約に留めることにした(ユーザーとの合意事項)。

### 案B: 現状維持(Planモードのみ、リポジトリに残さない)

新しい仕組みを増やさず、Plan モードの運用を人間側の規律(メモを取る、議事録を残す等)で補う案。
実装コストが最小という利点はあるが、根本原因(成果物が git に乗らない)を解決しないため、
同じ問題が再発することが確実だった。却下した。

### 案C: plan-reviewer を最初からゲート(FAILでCI失敗)にする

下流の `ai-qa.yml` と同じ強度で始める案。抜けのある計画を確実に止められる利点がある一方、
上流(要件・仕様)の良し悪しは下流(実装の正しさ)より判断がグレーになりやすく、
`ai-design-review.yml` が非ゲートで安定運用できている前例と比べても、初手からのゲート化は
誤検知による needs-human 運用の負荷が見合わないと判断した。design-reviewer と同じく
**非ゲート・レポートのみ**で開始し、精度が確認できてからゲート化を再検討する。

## 4. 結果

- 得られるもの: Issue → Plan PR → 実装PR の全過程が git に残り、`docs-lint.py` で機械検査できる。
  ADRにより「なぜその決定をしたか」が本文修正で消えず、`Superseded by` で積み上げられる。
- 引き受けたトレードオフ: ドキュメントの置き場所が増える(`.claude/06_adr/` / `.claude/07_plans/`)。
  腐敗を防ぐため、ADRは書き換えず積む運用、プランは `done` で凍結する運用とし、
  `docs-lint.py` にヘッダ検査を追加して機械的に守る(`04_development_process.md` §4・§5)。
- 撤回条件: Plan PR運用が実態に合わずオーバーヘッドだけが増えたと判断された場合、
  トリガー表(`04_development_process.md` §2)を緩めるか、本ADRを Superseded にして
  別方式へ切り替える。
