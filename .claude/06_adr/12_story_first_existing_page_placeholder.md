# 12. 既存画面の大きなレイアウト変更でもPlan PRストーリーにプレースホルダーを許可する

- Status: Accepted
- Issue: #173
- Date: 2026-08-13

## 1. 文脈

`.claude/06_adr/11_story_first_agreement.md`(案A)は、Plan PRの「コード0行」原則の例外として
対象画面の `.stories.tsx` を許可した。その際、新規画面(0→1)ではページ本体が存在しないため
ストーリー内にインラインのプレースホルダー実装を許可する一方、**既存画面の大きなレイアウト変更では
「本物のページを直importする(プレースホルダーは使わない)」**と定めた
(`04_development_process.md` §5.1、`10_frontend_design.md` §7)。

Issue #173(`LoginPage`/`TopPage` の大幅レイアウト変更)でこのルールを実際に使おうとしたところ、
矛盾が判明した。**既存画面の大きなレイアウト変更の時点では、本物のページ(`XxxPage.tsx`)はまだ
旧レイアウトのままである。** ルールどおり本物のページを直importすると、ストーリーは旧デザインを
表示してしまい、「実装前にNEWレイアウトを合意する」という `10_frontend_design.md` §7・Issue #170
の本来の目的を果たせない。

新規画面と既存画面の大規模変更は、どちらも「まだ実装されていない新しい見た目を、実装前に確認・
合意したい」という点で本質的に同じ課題であり、当初のADR 11・実装(PR #172)はこの点を見落としていた。

## 2. 決定

**既存画面の大きなレイアウト変更でも、新規画面(0→1)と同じ扱いにする。** Plan PRの
`.stories.tsx` には、提案する新レイアウトをストーリーファイル内にインラインのプレースホルダー
実装として書いてよい(`10_frontend_design.md` §7「ストーリー専用ダミー画面は作らない」原則の
Plan PR時点での例外を、既存画面にも拡張する)。実装PRで本物のページ(`XxxPage.tsx`)をこの
プレースホルダーの内容に合わせて書き換え、ストーリーを実importへ差し替える。

この決定は `04_development_process.md` §5.1・`10_frontend_design.md` §7・`03_feature_plan_template.md`
§3・`commands/plan.md` 手順5・`commands/pr.md` §3の「既存画面の大きなレイアウト変更では本物のページを
直importする」という記述を修正する。

**このADRは例外としてPlan PR内(本PR)で`Accepted`にし、上記5文書もPlan PR内で更新した。**
通常、Plan PRで新規作成するADRは`Proposed`のまま実装PRで`Accepted`にする(`04_development_process.md`
§4)が、本ADRの決定内容は「Plan PRの作り方」そのものであり、この決定を前提にした
`LoginPage.stories.tsx`/`TopPage.stories.tsx`(既存画面のプレースホルダー実装)を同じPlan PRに
含めている。決定をProposedのまま実装PR送りにすると、Plan PR自身が「まだ受理されていない決定」を
既成事実として使うという矛盾が生じるため、この場合に限り即時反映する
(`04_development_process.md` §4の例外規定を本ADRで初めて適用する)。

`.claude/06_adr/11_story_first_agreement.md` の中核の決定(案Aの採用・VRTスクリーンショット共有)
は変更しない。本ADRはその一部(既存画面ケースの扱い)を補正するものであり、ADR 11を
Supersededにはしない。

## 3. 却下した案

- **現行ルールのまま(本物のページを直import)**: 既存画面の大きなレイアウト変更ではストーリーが
  常に旧デザインしか表示できず、Issue #170が解決しようとした「実装前のUI合意」を果たせない。
  却下。
- **Plan PR時点では`.stories.tsx`を作らず、UI仕様は文章のみで確定させる**: 「実機を起動せずに
  UIを確認・合意する」という`10_frontend_design.md`§7の目的を、既存画面の大規模変更というまさに
  対象とすべきケースで放棄することになる。Issue #170の検証目的(Issue #173)自体が成立しなくなる。
  却下。
- **Plan PRで本物のページ(`XxxPage.tsx`)も書き換える**: 「Plan PRは`.stories.tsx`のみ例外」と
  いう原則(ADR 11)をさらに崩す。実装PRとPlan PRの境界(コードレビューの主体がReviewerか
  design-review/plan-reviewかという役割分担)も曖昧になる。却下。

## 4. 結果

**得るもの**: 新規画面・既存画面のレイアウト変更のどちらでも、実装前に「これから作る新しい見た目」を
ストーリーで確認・合意できるようになる。ADR 11が目指した効果が、既存画面ケースでも実質的に機能する。

**引き受けるトレードオフ**: 新規画面の場合と同じ二度書き(プレースホルダー→実装PRでの実import
差し替え)が、既存画面の大規模レイアウト変更でも発生する。

**撤回条件**: 運用してみてプレースホルダーと実装後のページの乖離が大きくなりがちだと分かった場合、
ADR 11の撤回条件と合わせて再検討する。
