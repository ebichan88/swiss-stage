# 11. 新規画面ストーリー先行作成をPlan PRの例外として認める

- Status: Proposed
- Issue: #170
- Date: 2026-08-12

## 1. 文脈

`.claude/01_development_docs/10_frontend_design.md` §7 と `.claude/00_project/03_feature_plan_template.md`
は、新規画面・大きなレイアウト変更では実装前にストーリー(`src/pages/XxxPage.stories.tsx`)を作成し、
実機を起動せずにUIを確認・合意すると定めている。

しかし実績上、この規定は運用されていない。`.stories.tsx` が追加された3回(#80, #121, #151)は
いずれも `feat:` の実装PR内での後付け作成であり、「新規画面をゼロから作る前にストーリーで合意した」
事例は存在しない。ストーリー作成と画面本体の実装が同一PRに同居しており、「実装前の合意ゲート」として
機能していない。

一方、`.claude/00_project/04_development_process.md` は Plan PR を「コード0行」と定めている(§1・§2)。
`.stories.tsx` はTypeScriptコードであり、素直にはPlan PRへ含められない。この矛盾を解消する必要がある。

検討した選択肢は3つ(Issue #170 記載):

- 案A: Plan PR の例外として `.stories.tsx` の追加のみ許可する
- 案B: Plan PR と実装PR の間に「ストーリー先行PR」を挟む
- 案C: 実装PR内で「ストーリー作成 → 人間が合意 → 実装」の順序を強制する

## 2. 決定

**案Aを採用する。** Plan PRの「コード0行」原則に例外を設け、新規画面・大きなレイアウト変更を含む
Plan PRには、対象画面の `src/pages/XxxPage.stories.tsx` を含めることを許可する。Plan PRのレビュー・
マージそのものを「UI合意」のゲートとして扱い、追加の機械的な逸脱検知の仕組み(VRTベースライン固定等)
は設けない。

新規画面(0→1)でページ本体(`src/pages/XxxPage.tsx`)がまだ存在しない場合に限り、ストーリーファイル
内にインラインのプレースホルダー実装を書くことをPlan PR時点で許可する(`10_frontend_design.md` §7の
「ストーリー専用ダミー画面は作らない」原則の例外)。実装PRで本物のページに差し替え、ストーリーを実
importへ書き換える。既存画面の大きなレイアウト変更では、この例外は使わず引き続き本物のページを直
importする。

詳細な運用ルール・対象範囲・更新する文書・DoDは同じPRのプラン(`.claude/07_plans/10_story_first_agreement.md`)
を参照。

**新規ストーリーのレビュー導線**: Plan PRに追加された新規ストーリー(＝対応するVRTベースライン画像が
まだ存在しないストーリー)は、既存の `.github/workflows/vrt.yml` を拡張し、スクリーンショットを
`actions/upload-artifact@v4` でartifact化したうえで、`notify` ジョブから「新規ストーリーのスクリーン
ショットをArtifactsからダウンロードできます」という案内をPRコメントに追記する。レビュアーがローカル
でStorybookを起動しなくても、PR上でUIの見た目を確認できるようにする。詳細設計はプランの技術設計を
参照。

## 3. 却下した案

- **案B(ストーリー先行PRを挟む)**: PR数が増え `/pr` の運用も変わる。シンプルさ優先の原則(CLAUDE.md
  最重要原則)に反する上、PRスタック運用(`commands/pr.md` §8)の管理コストが常設される。
- **案C(実装PR内で順序を強制)**: 「ストーリー作成 → 合意 → 実装」の合意ステップを、同一PR内で
  機械的・運用的に強制する手段がない(コミット順序をレビューする以外に検証方法がなく、実効性が薄い)。
  Issueが問題視した「ストーリー作成と実装が同居し事前合意ゲートとして機能しない」実態を変えられない。
- **VRTベースライン固定による機械的逸脱検知の追加**: Plan PRで作成したストーリーの初回スクリーンショット
  をVRTベースラインとして確定させ、実装PRでの見た目変更をVRT差分で検知する案も検討したが、追加の
  仕組みが複雑さを増す割に、他の設計判断(Plan PR承認)と同様に人間レビューで十分に代替できるため
  見送った。
- **新規画面をこの仕組みの対象外にする案**: 対象を「既存画面の大きなレイアウト変更」のみに絞れば
  「本番と同じ経路で直import」原則を崩さずに済むが、Issueが問題視した「新規画面での手戻り防止」
  という本来の目的(新規画面こそ手戻りコストが大きい)を達成できないため見送った。
- **スクリーンショットをPRブランチに直接コミットしraw.githubusercontent.com経由でインライン埋め込みする案**:
  ストーリーが差し替わるたびに画像がgit履歴に残り続け、リポジトリが肥大化するため見送った。
- **Storybookを外部ホスティング(GitHub Pages等)にプレビューデプロイしURLを共有する案**: 追加の
  ホスティングインフラとデプロイ管理コストが必要で、月$17予算・シンプルさ優先の原則(CLAUDE.md)に
  見合わないため見送った。既存の `vrt.yml` artifactアップロードで代替できる。

## 4. 結果

**得るもの**: 新規画面・大きなレイアウト変更において、実装前にストーリーを介したUI合意を取れるように
なる。既存のPlan PR承認フロー(`04_development_process.md` §1)にそのまま統合され、新しい承認プロセスを
発明せずに済む。あわせて、`vrt.yml` のartifactアップロード拡張により、レビュアーはローカルで
Storybookを起動しなくてもPR上のリンクからスクリーンショットを確認できるようになる。

**引き受けるトレードオフ**:

- Plan PRの「コード0行」原則が崩れ、説明が「原則0行、対象画面の`.stories.tsx`のみ例外」という形に
  複雑化する。
- 新規画面では、ストーリー内プレースホルダー実装 → 実装PRでの実import置き換え、という二度書きの
  手間が生じる。
- 既存の `ci.yml`(frontendジョブ)は path/イベント条件を変更しなくても、Plan PRブランチに
  `.stories.tsx` が追加されれば自動的に起動する。
- `vrt.yml` は path フィルタの変更なしに自動起動するが、新規ストーリーのartifactアップロード・
  PRコメント拡張には実装PRでのワークフロー変更が必要になる(§4参照)。新規ストーリーはVRTの初回
  実行でベースライン欠如により失敗するが、`vrt.yml` は非ブロッキング運用のため実害はない。

**撤回条件**: 運用してみて「プレースホルダー → 実装PRでの差し替え」の二度書きコストが高すぎると
分かった場合、または「コード0行」の例外化がPlan PRレビューを重くしすぎると分かった場合は、新しい
ADRを起こし案B・案Cへの切り替えを再検討する。
