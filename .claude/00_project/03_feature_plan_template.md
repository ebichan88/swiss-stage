# 機能追加プランのテンプレート

> Planモードで機能追加・挙動変更の実装計画を立てるときは、この形式に従う。
> 目的は **実装前にUIと画面シナリオの合意を取り、手戻りをなくすこと**。
>
> 対象: 新規画面の追加、既存画面のレイアウト変更、新しいユースケースの追加。
> 対象外: バグ修正、リファクタリング、ドキュメントのみの変更(該当セクションは省略してよい)。
> Plan PR・ADRの要否は `.claude/00_project/04_development_process.md` §2 のトリガー表に従う。

Plan PRでは、このテンプレートに沿って書いたファイルを `.claude/07_plans/NN_<slug>.md` として
リポジトリに残す(`04_development_process.md` §5)。ファイル冒頭に次のヘッダを付ける:

```markdown
# NN. <計画のタイトル>

- Status: planned
- Issue: #<Issue番号>
- PR: -
```

---

## 1. 背景・目的

なぜこの変更をするのか。解決する課題と、完了時に得られる状態。
判断に迷ったら `01_appcadia_concept_requirements.md` / `02_inception_deck.md` に立ち返る。

**最重要原則: 正確性 > シンプルさ > コスト > 機能 > 速度**

## 2. 画面シナリオ

「**誰が → どの画面で → 何をして → 何が起きる**」を箇条書きで列挙する。
ここが受け入れケース(§5)とE2Eの抽出元になるので、**正常系だけでなく異常系・境界も書く**。

```
- 運営者が 参加者一覧画面で CSVをインポートすると 参加者が一括登録され件数が表示される
- 運営者が 参加者0人の状態で 大会を開始しようとすると エラーメッセージが出て開始できない
- 参加者が 共有URLをスマホで開くと 自分の対局卓と対戦相手が表示される
```

観点の抜けチェック:

- 運営者(PC)と参加者(スマホ・ログイン不要)の**両方**を書いたか
- 個人戦と団体戦で挙動が変わるか
- グループ分けあり/なしで変わるか
- 競合(2人が同時に操作)・権限外アクセス・無効トークンの経路を書いたか

## 3. UI仕様

**このセクションが本テンプレートの中核。** 実装後に「物足りない」と気づく手戻りを防ぐため、
文章の段階でレイアウトと状態を確定させる。

記述の厚みは `.claude/02_design_system/00_basic_design.md` §4 の優先度に従う:
**1. 共有ページ(スマホ) > 2. 結果入力 > 3. 順位表 > 4. 運営者管理画面**(4はMUI標準に寄せてよい)。

対象画面ごとに以下を書く:

### 画面名

- **レイアウト構成**: 上から順に何が並ぶか。必要ならテキストのワイヤーフレーム
- **主要要素**: 見出し・ボタン(ラベルと配置順)・表の列・入力欄
- **4状態の見せ方**(データ取得がある画面では**必須**。`10_frontend_design.md` §2④):
  | 状態 | 表示 |
  |---|---|
  | 通常 | |
  | 空(0件) | 何を表示し、次に何をさせるか(EmptyStateのメッセージと導線) |
  | ローディング | |
  | エラー | メッセージと再試行導線 |
- **大量データ時**: 300人・全ラウンドでどう見えるか(スクロール・ページング・列の省略)
- **レスポンシブ**: 375px と デスクトップで何が変わるか
- **既存画面との一貫性**: 似た既存画面はどれか。ボタン配置・用語・トーンを合わせたか
- **新しいUIパターンの有無**: 必要なら **先に `02_component_design.md` に定義を追加してから実装する**

> 新規画面・大きなレイアウト変更では、ここに挙げた画面のストーリー(`src/pages/XxxPage.stories.tsx`)を
> **Plan PRの一部として作成する**(Plan PRの「コード0行」原則の例外。`04_development_process.md` §5.1)。
> Plan PRのレビュー・マージをもって「UI合意」とし、実機を起動せずに確認できるようにする。
> 新規画面(0→1)ではページ本体が未実装のため、ストーリー内にインラインのプレースホルダー実装を
> 書いてよい(実装PRで本物のページに差し替え、実importへ書き換える)。既存画面の大きなレイアウト
> 変更では、この例外は使わず本物のページを直importする(`10_frontend_design.md` §7)。

## 4. 技術設計

このプラン(`07_plans/NN_<slug>.md`)自体に技術設計を文章で書く。**`.claude/01_development_docs/**`
配下の設計ドキュメント本体はPlan PRでは更新しない**(実装PRで、実装コードと同じPRで更新する。
`04_development_process.md` §2。決定を書く場所をプラン1箇所に定め、プランと設計ドキュメントが
ずれて次のレビュー往復を生む事故を防ぐため)。

- **レイヤーごとの変更点**: domain / application / presentation / infrastructure(`01_architecture_design.md` のロジック配置基準に従う)
- **API変更**: あれば **`schema/openapi.yaml` を計画と同じPRで先に更新する**(API契約のSSoTで、
  Plan PRの対象に含まれる唯一の設計成果物)。エンドポイント・DTO・エラーコード
- **データモデル**: DynamoDBのキー・アクセスパターンの追加方針を文章で書く(`02_database_design.md` への反映は実装PR)
- **フロントエンド**: 追加するページ / features / ui コンポーネント、hooks と queryKey
- **マッチング・順位計算に触れる場合**: 変更方針を文章で書く(絶対制約の再戦禁止・BYE重複禁止を
  弱めないこと)。`05_swiss_pairing_algorithm.md` への反映は実装PRで、実装コードより先に行う

## 5. 受け入れケース

`.claude/05_acceptance/00_acceptance_policy.md` の体系(`<PREFIX>-AC-<3桁連番>`)に従って、
追加・変更するケースを列挙する。**実装前に台帳へ Status=todo で追加し、実装PRで done にする。**

ケースの洗い出しには `.claude/01_development_docs/09_test_strategy.md` §2.5 の技法を使う。
特に §2 の画面シナリオから起こしたケースに対して、**境界値(両側)と条件の組み合わせの抜け**を確認する。

| ID | P | 受け入れ基準 | 検証手段 |
|---|---|---|---|
| | | | contract / Vitest / E2E |

- 連番は永久欠番・再利用禁止。既存の最大値+1から採番する
- 優先度は `.claude/04_quality/02_severity.md` の判定フローに従う(P0=大会当日に運営が止まる/結果が狂う/情報漏れ)
- API契約に変化がなくUI表示のみのケースは、Vitest単体テストを検証手段にしてよい

## 6. 更新する資料

### Plan PRで更新するもの

更新対象のファイルを**事前に列挙する**。プラン承認 = この範囲の更新の承認。

- [ ] `.claude/05_acceptance/01_acceptance_scope.md` — ケース追加(ほぼ常に対象)
- [ ] `.claude/06_adr/NN_<slug>.md` — ADRを書く条件(`04_development_process.md` §3)に当たる場合
- [ ] `schema/openapi.yaml` — API変更がある場合(実装より先)
- [ ] `src/pages/XxxPage.stories.tsx` — 新規画面・大きなレイアウト変更の場合(`04_development_process.md` §5.1)

### 実装PRで更新が必要な設計ドキュメント(今は更新しない・実装時の申し送り)

- [ ] `.claude/01_development_docs/05_swiss_pairing_algorithm.md` — マッチング・順位計算の仕様変更がある場合(実装コードより先に更新する)
- [ ] その他(`02_database_design.md` / `04_screen_transition_design.md` / `06_error_handling_design.md` / `02_component_design.md` …)

## 7. DoD(完了の定義)

**DoDは主要シナリオが動くことを確認する完了条件であり、境界値・条件の組み合わせを網羅する
テスト設計ではない**(それは §5 受け入れケースと `09_test_strategy.md` §2.5 の責務)。
§5を「該当なし」とした場合の受け皿としてDoDに項目を積み増さないこと。

- [ ] `pnpm run check`(frontend)/ `./gradlew check`(backend)が通る
- [ ] 受け入れケースが台帳で done になり、対応するテストにIDが埋まっている
- [ ] **新規画面には最低1本のsmoke E2E**(表示できる + 主要導線を1回通す)、または既存クリティカルパスへの検証追加がある
- [ ] §6「実装PRで更新が必要な設計ドキュメント」が実装PRで更新されている
- [ ] ローカル実機で動作確認済み(`.claude/skills/verify`)
- [ ] 大きめのUI変更(新規画面・レイアウト変更)の場合、`vrt.yml` を手動実行してベースラインを更新した(`09_test_strategy.md`)

## 8. リスク・未確定事項

判断を要する点、後戻りが高くつく決定、中止条件があれば書く。
**不確実な技術要素はスパイクを先に置き、失敗時にどうするかまで決めておく。**
